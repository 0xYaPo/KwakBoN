Bon, maintenant si je veux tester ce qu'on a prévu de faire est-ce qu'on va perdre les fonds sur battle ou bien on s'envoie entre les wallets qu'on possède ?
On s'envoie entre les wallets qu'on possède — c'est exactement ce que fait cmd/windowsprint.

Le flow Window A :

Treasury → senders (fundwallets) : distribue des EGLD aux 150 wallets active_candidate
Senders → receiver (windowsprint) : chaque sender envoie des MoveBalance vers un receiver qu'on contrôle (le wallet receiver dans le manifest)
Senders → treasury (sweepwallets) : rapatrie ce qui reste
Aucun EGLD ne quitte ton périmètre — tu perds juste les frais de gas sur chaque tx. D'après le rehearsal du 15 mars, 110 EGLD distribués → 107.11 EGLD récupérés, soit ~2.9 EGLD de frais pour 20 000 tx à 800 TPS.

Donc pour un test : tu peux lancer un petit run (ex. 500 tx à 50 TPS) en --dry-run d'abord, puis pour de vrai — tu perdras quelques centimes de gas et tout le reste revient à la treasury via le sweep.

Ok, je voudrai tester pleine balle pour voir si j'arrive à obtnri ce qu'il y a dans le manifeqst, je dois set up un node ?
Non, pas besoin de node pour Window A.

windowsprint envoie juste des transactions via le gateway API — il n'est pas validateur lui-même. Ton code tape sur https://api.battleofnodes.com (ou devnet pour tester) et les validateurs du réseau traitent les tx.

Le node c'est pour :

Challenges 1-3 (être validateur)
Window B (DEX calls, qui peuvent nécessiter d'interagir avec ton propre node)
Pour tester Window A pleine balle maintenant, tu as besoin de :

.env complet (treasury address + PEM, manifest path, params de sprint)
Wallets fundés — soit sur battle, soit sur devnet pour un vrai test sans risque
La question clé : tu veux tester sur battle directement (frais réels, ~3 EGLD pour un gros run) ou sur devnet avec tes wallets ? Sur devnet les wallets shard-2 ne seront pas les mêmes shards qu'en battle, donc les résultats TPS seront différents — mais ça valide le code.

Voilà la logique expliquée :

Window A (shard-2 uniquement)

250 wallets (active_candidate + warm_reserve) filtrés sur shard 2
Tx intra-shard = le plus rapide possible
~110 EGLD distribués, ~3 EGLD de frais
FUND_REQUIRED_TAGS=window_a pour ne cibler que les wallets Window A
Window B (tous shards)

497 wallets (+ les window_b_reserve sur shards 0 et 1)
3 receivers — un par shard — pour que les tx restent intra-shard même cross-pool
~497 EGLD distribués
FUND_REQUIRED_TAGS=sender pour inclure tous les wallets actifs
